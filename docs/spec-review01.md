# 仕様書レビュー 01

対象: SPEC.md v0.1
日付: 2026-05-14

## 総評

現状のままでは実装に着手するには不十分。方向性・構造・技術方針は良いが、「実際にコードを書く」段階で必ず詰まる箇所が複数ある。

---

## A. 矛盾・不整合

### A-1. `Plot` 型が WorldState に登場するが定義がない

`WorldState` に `activePlots?: Record<PlotId, Plot>` があるのに、`Plot` 型の定義が仕様書内にない。`PlotId` も同様。PlotSystem の説明には「スコアが閾値を超えたら発生」とあるだけで、陰謀の **状態（進行中/解決済み）、期間、関与者、ターゲット** が何も定義されていない。

### A-2. `War` 型も未定義

`activeWars?: Record<WarId, War>` が WorldState にあるが、スコープ 3.2 では「詳細な戦争シミュレーションは含めない」とされている。反乱解決は数値比較で行うとあるので、`War` エンティティが必要かどうかすら不明。反乱を War として扱うのか、別物なのか判断できない。

### A-3. Province の `ownerHouseId` と `countryId` の同期管理が未定義

整合性チェック（18.5）で「Province の ownerHouseId と countryId が矛盾していないか」をチェックするとあるが、どのシステムがこれを更新するのかが書かれていない。反乱成功時に領地没収する際、Province 側の `countryId` と House 側の `provinceIds` の**どちらを正として更新するか**のルールがない。

### A-4. Person.role と Country.roleAssignments の二重管理

`Person` に `role: RoleType | null` があり、`Country` にも `roleAssignments: Partial<Record<RoleType, PersonId>>` がある。どちらが source of truth かが明示されていない。任命・解任時に両方を同期する必要があるが、「どちらから読むか」「どちらを先に更新するか」の規約がないと不整合の温床になる。

### A-5. House.headId と IntegrityCheck の意図が曖昧

`House.headId` に対応する人物が `alive: false` になった際、SuccessionSystem が動くはず。tick 順序（死亡→継承）でカバーできる話だが、IntegrityCheck の「家長が死亡していないか」チェックは「継承後もまだ死亡家長が残る場合はエラー」という意図なのか、「死亡直後にすでに家長が更新されているべき」なのかが不明。明示が必要。

---

## B. 未定義・不足している部分

### B-1. 世界生成（generateWorld）の具体的なルールが皆無

「30〜50プロヴィンス、3国家、15家、100人」という目標数値はあるが、生成アルゴリズムの方針が何もない。実装時に必ず必要になる事項：

- プロヴィンスの隣接グラフをどう生成するか（完全ランダム？格子状？）
- 国家への割り当てはどう決めるか（連続した地域を1国家にするか）
- 家とプロヴィンスの対応はどう決めるか（1家＝複数プロヴィンス？）
- 人物の初期年齢分布はどうするか（家長は成人以上、など）
- 各パラメータの初期値範囲はどこか（`baseTax` は 1〜10？ `prestige` は 0〜100？）

**パラメータの値域が仕様書全体を通じて一切定義されていない。** イベント例では `ambition: 0.88`、`legitimacy: 32` のように数値が出てくるが、それぞれのスケール（0〜1 か 0〜100 か）が混在しているように見える。

### B-2. RNG の仕様が未定義

「seed 付き RNG を使う」とあるだけで、アルゴリズム（xorshift? Mulberry32? PCG?）、シードの型（number? string?）、RngState の構造が定義されていない。「同一 seed で同じ展開」を保証するためにも、ここは具体的に決める必要がある。

### B-3. PlotSystem の陰謀の「解決」ロジックが未定義

「スコアが閾値を超えたら発生」「成功/失敗のイベントがある」とあるが、以下が未定義：

- 陰謀は何 tick かけて解決するのか（即時？複数月？）
- 誰が誰に対して行う陰謀なのか（Person → Person? House → House?）
- 成功・失敗の判定式は？（PlotSystem には書かれていない）
- 反乱準備の陰謀が成功したら RebellionSystem にどう接続されるのか

### B-4. 国家分裂（COUNTRY_SPLIT）の後処理が未定義

反乱成功時に「新国家として独立」とあるが、以下が未定義：

- 新しい CountryId、Country オブジェクトをどう生成するか
- 独立国の初期 `legitimacy`、`treasury` はどう決まるか
- 元国家の `houseIds` から独立した家をどう除くか
- 独立国の `rulerHouseId` は反乱家か
- 独立後の隣接国との関係（スコープ外とするなら明記を）

### B-5. StabilitySystem の具体的な更新量が未定義

「legitimacy が少し回復」「legitimacy が低下」などの方向性はあるが、**具体的な変化量、適用条件、上限・下限** が書かれていない。SimulationConfig に切り出すとあるが、デフォルト値の目安もない。

### B-6. AppointmentSystem の任命頻度が未定義

「空席になったら次の tick で誰かを任命する」のか、「N ヶ月に1回評価する」のか、「treasury が足りないと任命できない」のか、全く書かれていない。

### B-7. 人物の誕生（世代交代）が未定義

MortalitySystem で人物は死亡するが、新しい人物がどのタイミングで、どのような条件で生まれるかが書かれていない。出生なしでは100人が死に続けてシミュレーションが停止する。人口補充（出生）の仕様が必要。

### B-8. 家の断絶（HOUSE_EXTINCT）後の処理が未定義

`HOUSE_EXTINCT` イベントが定義されているが、断絶した家の後処理が未定義：

- `provinceIds`（領地）はどこに移るか
- `memberIds` は全員死亡しているのか、それとも他家に移籍するのか
- `countryId` の `houseIds` からの除去タイミング
- Province の `ownerHouseId` は何になるか

### B-9. 陰謀の種類ごとの効果が未整理

「家長交代の陰謀」「役職奪取の陰謀」「反乱準備の陰謀」の3種が列挙されているが、それぞれの**成功時の具体的な状態変化**が書かれていない。特に「家長交代の陰謀」が成功したとき、現家長はどうなるか（死亡？失脚？）が不明。

## C. 曖昧・解釈が割れる部分

### C-1. `legitimacy`、`adminPower`、`stability` の関係が曖昧

3つの値の関係が不明：

- `stability` と `legitimacy` は何が違うのか（短期 vs 長期？）
- `adminPower` は蓄積するリソースなのか、状態値なのか
- どの値が反乱判定に使われ、どれが単なる表示用なのか

### C-2. 「反乱中」の状態管理が未定義

`REBELLION_STARTED` が発行されてから `REBELLION_SUCCEEDED`/`REBELLION_FAILED` までの間、世界はどういう状態にあるのか不明：

- 反乱は**即時解決**（同じ tick 内）するのか、**複数 tick にわたる**のか
- `WorldState` に `activeWars` があることから「複数 tick」のように見えるが、スコープ外の戦争システムとの関係が不明

### C-3. Province の `manpower` の使い道が未定義

`Province` に `manpower` フィールドがあるが、RebellionSystem の `rebelPower` 計算には登場しない。使い道が不明なまま定義されている。

### C-4. House の `cohesion` の使い道が曖昧

「低いと家内陰謀が起きやすい」とだけあり、PlotSystem との接続が明示されていない。

### C-5. 「家の忠誠」と「人物の忠誠」の関係

`House.loyaltyToCountry` と `Person.traits.loyaltyToCountry` が両方ある。どちらが反乱判定に効いて、どう計算されるのか不明。反乱傾向の計算式には「家長の国家忠誠」が使われており、人物側だけ見えるが、家側の値の役割が曖昧。

## D. 技術的に実現が難しい部分

### D-1. 「決定性」とオブジェクト列挙順

14.2 で「オブジェクト列挙順に依存する非決定的処理を禁止」とあるが、`Record<Id, T>` を `Object.values()` で列挙するとキーの挿入順に依存する。ID を**ソートした上でイテレート**する規約が必要。これはコーディング規約レベルの話だが、仕様書に明記すべき。

### D-2. 長期シミュレーションのメモリ肥大化

`eventHistory: SimEvent[]` を WorldState に持つと、200年（2400 tick）× 毎月多数のイベントでメモリが肥大化する。仕様書では「tick 結果として外部蓄積してもよい」とあるが、曖昧なままにしておくとシリアライズ設計にも影響する。

## 優先度別まとめ

### 実装前に必ず決めるべき（ブロッカー）

1. パラメータの値域（0〜1 か 0〜100 か、各フィールドを統一）
2. RNG の具体的なアルゴリズムと RngState 型
3. Plot 型の定義（状態、ターゲット、継続期間）
4. 反乱の「即時解決 vs 複数 tick」の判断
5. 人物の誕生（出生）ルール
6. Province と House の同期ルール（source of truth）
7. 世界生成の基本アルゴリズム方針

### 実装中に決めても間に合う（中優先）

1. War 型の要否（反乱を War として扱うか否か）
2. StabilitySystem の具体的な変化量
3. AppointmentSystem の任命頻度ルール
4. 家断絶後の領地移転先

### 後回しにできる（低優先）

1. eventHistory の保持場所の最終決定
2. Chronicle 表示の閾値
3. 重要人物スコアの重み係数
